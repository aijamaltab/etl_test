# ETL платежей: CSV -> PostgreSQL

Загрузка платежных операций из CSV-файлов в PostgreSQL. Каждая строка проходит проверки качества, плохие строки сохраняются с причинами, исправления из следующих файлов обновляют платежи, повторный запуск ничего не ломает.

Python отвечает за файлы: порядок, реестр, чтение CSV. Все проверки строк и запись в таблицы сделаны на SQL, set-based, внутри одной транзакции на файл.

Нужны PostgreSQL 13+ и Python 3.8+. Проверено на PostgreSQL 14.

## Быстрый старт

```bash
pip install -r requirements.txt

# подключение - стандартные переменные libpq
export PGHOST=localhost PGPORT=5432 PGUSER=... PGPASSWORD=... PGDATABASE=...

# схема и объекты
psql -c "CREATE SCHEMA IF NOT EXISTS payments_etl;"
PGOPTIONS='-c search_path=payments_etl' psql -v ON_ERROR_STOP=1 -f sql/create_tables.sql
PGOPTIONS='-c search_path=payments_etl' psql -v ON_ERROR_STOP=1 -f sql/payments_running_count.sql

# загрузка
python3 etl/load_payments.py data

# нарастающий итог по датам
psql -c "SELECT * FROM payments_etl.payments_running_count();"

# проверка решения (в отдельной схеме payments_etl_test)
python3 tests/run_checks.py
```

Настройки через переменные окружения:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` | - | подключение к PostgreSQL |
| `ETL_SCHEMA` | `payments_etl` | схема, в которую грузим |
| `ETL_TIMEZONE` | `Asia/Bishkek` | от чего считается "сегодня" в проверке "дата в будущем" |

В SQL-файлах схема не указана, она берется из `search_path`. Поэтому решение можно развернуть в любой схеме без правки файлов. Если схема не `payments_etl`, поменяйте ее в командах выше и задайте `ETL_SCHEMA`.

## Главные решения

Подробно каждое расписано ниже, здесь коротко.

1. **Формат CSV разбираю в Python, проверки строк делаю в SQL.** `COPY` напрямую из файла падает целиком на одной кривой строке, а проверки на SQL работают сразу со всем файлом и масштабируются.
2. **Один файл - одна транзакция.** Упал - откатился целиком, статус `failed`, можно перезапустить. Ошибка в строке файл не роняет, строка уходит в `payments_rejected` со всеми причинами.
3. **Повторный запуск защищен дважды.** Реестр файлов по sha256 пропускает уже загруженные файлы, а номер файла в каждом платеже (`source_seq`) не дает старому файлу откатить новую версию.
4. **Версии платежа упорядочивает только порядок файлов.** Исправление из следующего файла обновляет платеж. Две разные версии в одном файле не угадываю: отклоняю обе, верная приходит следующим файлом.
5. **Ошибка на уровне файла останавливает очередь.** Следующие файлы могут исправлять платежи из упавшего, грузить их раньше нельзя.
6. **"Период" в нарастающем итоге задается параметрами.** Дополнительно считаю итог с начала месяца - на случай, если имелся в виду месяц.
7. **"Добавлено" в статистике - только новые платежи.** Исправления считаются отдельно, в "обновлено".

## Как работает загрузка

1. Беру advisory lock на всю сессию: два запуска одновременно не пойдут, второй сразу выйдет с кодом 2.
2. Загружаю `contracts.csv`. Если в справочнике ошибка (повтор ID, пустое поле, плохая дата), останавливаюсь: без справочника проверять платежи бессмысленно.
3. Беру файлы `payments_NNN.csv` и сортирую по номеру. Файлы с другим именем пропускаю с предупреждением.
4. Для каждого файла:
   - считаю sha256 и сверяюсь с реестром `load_files` (правила ниже);
   - регистрирую файл со статусом `processing`;
   - читаю CSV в Python (BOM, заголовок, пустые строки, число полей) и через `COPY` кладу во временную staging-таблицу, все колонки `text`;
   - SQL проверяет каждую строку, ищет дубли и решает, что с ней делать: `insert`, `update`, `unchanged` или `reject`;
   - одним запросом записываю новые платежи, исправления и отклоненные строки;
   - сверяю количество и ставлю файлу `success` со статистикой.

   Все это одна транзакция. Если что-то упало, откатывается весь файл, он получает `failed`, и его можно спокойно перезапустить.
5. Печатаю статистику.

Почему не `COPY` сразу из файла: `COPY` падает на всем файле, если в одной строке лишняя колонка. По условию ошибка строки не должна останавливать остальные, поэтому формат CSV разбираю в Python, а в базу кладу уже разобранные строки.

По сути это ETL: в целевые таблицы попадают только проверенные данные. Просто "T" выполняет PostgreSQL во временной таблице, а не Python построчно.

## Модель данных

| Таблица | Что хранит | Grain |
|---|---|---|
| `payments` | итоговые платежи | одна строка на `payment_id`, последняя корректная версия |
| `payments_rejected` | отклоненные строки: сырые значения и все причины | одна строка на строку файла |
| `load_files` | реестр файлов: статус, hash, статистика, код ошибки | одна строка на содержимое файла |
| `contracts` | справочник договоров | одна строка на `contract_id` |
| `ref_currency` | допустимые валюты: KGS, USD, EUR, RUB | одна строка на валюту |

Что стоит отметить:
- В `payments` есть `source_file_id` (из какого файла текущая версия) и `source_seq` (номер этого файла). `source_seq` дублирует номер из реестра, чтобы проверять порядок версий прямо в `UPDATE`, без JOIN.
- В таблицах стоят `CHECK` и внешние ключи, хотя все то же самое уже проверено в SQL. Это последний рубеж: если в валидации баг, файл упадет, а не загрузит плохие данные тихо.
- Валюты лежат в таблице, а не в коде. Новая валюта - это одна строка `INSERT`.
- `raw_values` в rejects хранится jsonb-массивом: так сохраняется и строка с лишними колонками.

## Проверки качества данных

Проверки на двух уровнях.

**Уровень файла (Python).** Если не прошло, файл не грузится, следующие файлы в этом запуске тоже. Они могут исправлять платежи из упавшего файла, и грузить их раньше нельзя.

| Код | Когда |
|---|---|
| `FILE_ENCODING` | файл не в UTF-8 (BOM допускается) |
| `FILE_HEADER_MISMATCH` | заголовок не `payment_id,contract_id,prov_dt,amount,currency` |
| `FILE_EMPTY` | нет строк с данными |
| `FILE_CONTENT_CHANGED` | файл с таким именем уже загружен, а содержимое другое |
| `FILE_OUT_OF_ORDER` | номер файла меньше уже загруженного |
| `CONTRACTS_INVALID` | ошибка в `contracts.csv`, останавливается весь запуск |

**Уровень строки (SQL).** Строка уходит в `payments_rejected`, остальные строки файла грузятся. Причины накапливаются: если в строке три ошибки, будет три кода.

| Код | Проверка |
|---|---|
| `COLUMN_COUNT_MISMATCH` | в строке не 5 полей (остальные проверки для нее не делаются) |
| `MISSING_PAYMENT_ID`, `MISSING_CONTRACT_ID`, `MISSING_PROV_DT`, `MISSING_AMOUNT`, `MISSING_CURRENCY` | поле пустое |
| `INVALID_PAYMENT_ID` | не `^[A-Z0-9_-]{1,30}$` |
| `CONTRACT_NOT_FOUND` | договора нет в справочнике |
| `INVALID_DATE` | не `ГГГГ-ММ-ДД` или такой даты нет (`2026-09-31`) |
| `DATE_BEFORE_CONTRACT_OPEN` | платеж раньше открытия договора |
| `DATE_IN_FUTURE` | дата позже сегодняшней (по `ETL_TIMEZONE`) |
| `INVALID_AMOUNT` | не число вида `123` или `123.45` (`12,50`, `NaN`, `1e3` не проходят) |
| `NON_POSITIVE_AMOUNT` | сумма <= 0 |
| `AMOUNT_SCALE` | больше 2 знаков после точки |
| `AMOUNT_TOO_LARGE` | не влезает в `numeric(18,2)` |
| `INVALID_CURRENCY` | валюты нет в `ref_currency` |
| `DUPLICATE_ROW` | точная копия строки выше в этом же файле |
| `DUPLICATE_KEY_CONFLICT` | у одного `payment_id` в файле разные версии |

Перед проверками у значений обрезаются пробелы, пустая строка считается отсутствием значения, валюта приводится к верхнему регистру. ID не трогаю: `p1` и `P1` у источника могут быть разными платежами.

Даты и суммы разбираю без `::date` на сыром тексте: `'2026-09-31'::date` дал бы ошибку на весь файл. Сначала формат регуляркой, потом проверка, что такой день есть в месяце, и только потом приведение.

Отдельно - сверка самого пайплайна по каждому файлу:
`прочитано = добавлено + обновлено + без изменений + отклонено`, и записано ровно столько, сколько решили. Не сошлось - файл откатывается с `RECONCILIATION_FAILED`.

## Дубли и исправления

**Внутри одного файла:**
- одинаковые строки (P021) - первая идет дальше, остальные `DUPLICATE_ROW`;
- разные версии одного `payment_id` (P022, P023) - отклоняю все с `DUPLICATE_KEY_CONFLICT`.

Почему не "берем последнюю строку" или "берем с максимальной датой": по условию версии упорядочивает только порядок файлов, внутри файла порядка версий нет. `prov_dt` - дата проведения, а не время изменения, исправление может сдвигать ее назад. А если это два разных платежа с одним ID, выбор любой строки молча теряет платеж. Поэтому не угадываю: обе строки в rejects, верная версия приходит следующим файлом (P022 в `payments_003.csv`). Если источник начнет передавать версию записи (`version`, `change_ts`), правило можно поменять на "побеждает последняя версия".

Рассматривала вариант оставлять положительную сумму, если версии отличаются только знаком (P023: 100 и -100). Отказалась: отрицательная сумма может быть сторно, тогда загрузился бы отмененный платеж.

**Между файлами:**
- корректная строка из более позднего файла обновляет платеж (P005, P001, P028);
- некорректная правка отклоняется, платеж остается прежним (P007);
- строка, совпадающая с текущей версией, ничего не меняет (P006).

## Повторный запуск

Две линии защиты.

**Реестр файлов `load_files`** с sha256 содержимого:

| Ситуация | Что делаю |
|---|---|
| такой hash уже загружен | пропускаю (`skipped`); если имя другое - предупреждение в лог |
| имя уже загружено, hash другой | `FILE_CONTENT_CHANGED`: принятый файл не подменяется, исправления идут новым номером |
| номер меньше уже загруженного | `FILE_OUT_OF_ORDER` |
| файл был `failed` или `processing` | обрабатываю заново: прошлый запуск упал, от него ничего не осталось |

Уникальный индекс на имя файла частичный (`WHERE status = 'success'`): успешный файл с одним именем может быть только один, а неудачных попыток сколько угодно. Так можно перезалить исправленный файл после падения, и история падения остается.

**`source_seq` в платежах.** Даже если реестр по какой-то причине не сработал, файл не может откатить версию из более нового файла. Если такое обнаруживается, файл падает с `VERSION_CONFLICT` и откатывается целиком.

Статус `processing` на старте значит, что прошлый запуск упал: лок сессионный, снимается сам при падении процесса, так что живой параллельный запуск исключен.

## Статистика

```
payments_001.csv   processed | прочитано   29 | отклонено   21 | добавлено    8 | обновлено    0 | без изменений    0
payments_002.csv   processed | прочитано    8 | отклонено    1 | добавлено    4 | обновлено    2 | без изменений    1
payments_003.csv   processed | прочитано    4 | отклонено    0 | добавлено    3 | обновлено    1 | без изменений    0
ИТОГО                        | прочитано   41 | отклонено   22 | добавлено   15 | обновлено    3 | без изменений    1
Всего платежей в таблице: 15
```

- "Добавлено" - новые `payment_id`. Исправления существующих платежей - отдельно, в "обновлено".
- "Обновлено" и "без изменений" добавила сверх ТЗ: без них не сходится сверка и не видно, как отработали исправления.
- Пустые строки не считаются прочитанными, их количество пишется в лог. Строка `,,,,` - это запись с пустыми полями, она проверяется как обычно.
- Статистика каждого файла сохраняется в `load_files`, при повторном запуске ее можно посмотреть там:

```sql
SELECT file_name, status, rows_read, rows_rejected, rows_inserted, rows_updated, rows_unchanged,
       finished_at - started_at AS duration
FROM payments_etl.load_files
ORDER BY file_id;
```

Время в логах - время сервера со смещением (`+0000` = UTC), чтобы его можно было сопоставить с логами других систем.

## Нарастающий итог по датам

`sql/payments_running_count.sql` создает функцию `payments_running_count(date_from, date_to)`.

Что такое "период", в задании не сказано, поэтому:
- период задается параметрами; если их не передать - от первого до последнего платежа;
- `cnt_from_period_start` - итог с начала периода;
- `cnt_mtd` - итог с начала месяца, на случай если под периодом имелся в виду месяц.

Выводятся все даты периода, в дни без платежей 0. Считаются текущие версии платежей: если исправление перенесло дату, платеж считается под новой. Отклоненные строки не считаются.

Тестовые платежи датированы сентябрем 2026, проще всего вызвать без параметров:

```sql
SELECT * FROM payments_etl.payments_running_count();
SELECT * FROM payments_etl.payments_running_count('2026-08-30', '2026-10-02');  -- видно сброс cnt_mtd 1 октября
```

```
     dt     | cnt_day | cnt_from_period_start | cnt_mtd
------------+---------+-----------------------+---------
 2026-09-03 |       1 |                     1 |       1
 2026-09-04 |       2 |                     3 |       3
 2026-09-05 |       0 |                     3 |       3
 ...
 2026-09-25 |       1 |                    15 |      15
```

## Проверка решения

`tests/run_checks.py` - интеграционный тест на эталонных данных. В отдельной схеме `payments_etl_test` создает таблицы теми же SQL-файлами, запускает загрузчик как отдельный процесс и SQL-запросами сверяет результат с ожидаемым. Основную схему не трогает, тестовую в конце удаляет.

```bash
python3 tests/run_checks.py
...
Все проверки пройдены: 28
```

| Требование ТЗ | Чем подтверждено |
|---|---|
| загрузка CSV в PostgreSQL с проверками качества | блок 1: три файла загружены, 22 строки отклонены |
| отклоненные записи сохраняются с причинами | блок 2: причина есть у каждой строки, несколько ошибок - несколько причин |
| корректная запись из следующего файла обновляет платеж | блок 3: P005 исправлен, P022 загружен после конфликта, P007 не испорчен |
| повторная обработка не создает дублей и не меняет данные | блок 4: файлы пропущены, снимок платежей до и после совпадает |
| ошибка строки не останавливает остальные | блок 1: в 001 отклонена 21 строка, остальные 8 загружены |
| статистика: прочитано, отклонено, добавлено | блок 1: статистика по каждому файлу |
| SQL нарастающего итога по датам | блок 5: итог 15, дни без платежей дают 0 |
| сверх ТЗ: принятый файл нельзя подменить | блок 6: `FILE_CONTENT_CHANGED`, данные не тронуты |
| сверх ТЗ: битый файл останавливает очередь | блок 7: следующий файл ждет, после исправления все грузится |

В тест не вошли, но обработаны в коде: параллельный запуск (второй выходит с кодом 2), старый файл в обход реестра (`VERSION_CONFLICT`), файл не по порядку (`FILE_OUT_OF_ORDER`), копия файла под другим именем (пропуск с предупреждением), битый справочник договоров (`CONTRACTS_INVALID`).

## Если файл упал

1. Смотрю причину: `SELECT file_name, error_code, error_message FROM payments_etl.load_files WHERE status = 'failed';`
2. Ошибка в файле (`FILE_HEADER_MISMATCH`, `FILE_ENCODING`, `FILE_EMPTY`) - источник присылает исправленный файл под тем же именем, запускаю загрузку снова.
3. `FILE_CONTENT_CHANGED` или `FILE_OUT_OF_ORDER` - нарушен порядок файлов, нужно разбираться с источником. Исправления должны приходить новым файлом со следующим номером.
4. `UNEXPECTED_ERROR` (например, упала база) - транзакция откатилась, просто перезапускаю.

Пока файл не исправлен, следующие файлы не грузятся.

## Допущения

- Порядок файлов задается номером в имени `payments_NNN.csv`.
- Отрицательная или нулевая сумма - ошибка. Возвраты и сторно - отдельный тип операции, которого в формате нет.
- Десятичный разделитель - точка. `12,50` не исправляю автоматически.
- Исправление может менять любые поля платежа, включая `contract_id`.
- `payment_id` и `contract_id` чувствительны к регистру.
- Если строка отклонена, а потом пришла исправленной, запись в rejects остается как история.
- Справочник договоров грузится целиком при каждом запуске upsert'ом, договоры не удаляются.

## Что бы сделала дальше

- История версий платежа: append-only `payments_history`, куда в той же транзакции пишется каждая версия.
- История запусков: таблица `load_runs`. Сейчас `skipped` виден только в логе, в реестре хранится состояние файла, а не события запуска.
- Тест на pytest с запуском в CI на каждое изменение, база - одноразовый контейнер.
- Алерты по `load_files`: файл в `processing` дольше часа, доля отклонений выше порога, файл в `failed`.
- Запуск по расписанию из Airflow: загрузчик уже возвращает понятные коды выхода (0, 1, 2) и безопасен для retry.
- Миграции схемы через Flyway или Liquibase вместо `IF NOT EXISTS`.
- Замер на большом файле (генератор с фиксированным seed на 100k+ строк).

### Если переносить на Vertica

- Загрузка та же: `COPY` пачкой в staging и set-based SQL дальше.
- Staging и `payments` сегментировать по `payment_id`, чтобы JOIN при классификации шел локально на узлах.
- Вместо `INSERT ... ON CONFLICT` и `UPDATE` - `MERGE`.
- DDL в Vertica коммитится сразу, транзакция вокруг него не поможет. Скрипты должны быть перезапускаемыми (`IF NOT EXISTS`), как здесь.
- Ограничения в Vertica по умолчанию не проверяются при загрузке, поэтому валидация в ETL там еще важнее.
