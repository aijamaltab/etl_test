# ETL платежей: CSV -> PostgreSQL

Загрузка платежных операций из CSV-файлов в PostgreSQL. Каждая строка проходит проверки качества, плохие строки сохраняются с причинами, исправления из следующих файлов обновляют платежи, повторный запуск ничего не ломает.

Нужны PostgreSQL 13+ и Python 3.8+. Проверено на PostgreSQL 14.

## Быстрый старт

```bash
pip install -r requirements.txt

# подключение - стандартные переменные libpq
export PGHOST=localhost PGPORT=5432 PGUSER=... PGPASSWORD=... PGDATABASE=...

# схема и объекты
psql -c "CREATE SCHEMA IF NOT EXISTS payments_etl;"
PGOPTIONS='-c search_path=payments_etl' psql -v ON_ERROR_STOP=1 -f sql/create_tables.sql
PGOPTIONS='-c search_path=payments_etl' psql -v ON_ERROR_STOP=1 -f sql/payments_running_count.sql

# загрузка
python3 etl/load_payments.py data

# нарастающий итог по датам
psql -c "SELECT * FROM payments_etl.payments_running_count();"

# проверка решения (в отдельной схеме payments_etl_test)
python3 tests/run_checks.py
```

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` | - | подключение к PostgreSQL |
| `ETL_SCHEMA` | `payments_etl` | схема, в которую грузим |
| `ETL_TIMEZONE` | `Asia/Bishkek` | от чего считается "сегодня" в проверке "дата в будущем" |

В SQL-файлах схема не указана, она берется из `search_path`, поэтому решение разворачивается в любой схеме без правки файлов.

## Главные решения

1. **Формат CSV разбираю в Python, проверки строк делаю в SQL.** `COPY` напрямую из файла падает целиком на одной кривой строке. Поэтому Python читает файл и кладет строки через `COPY` во временную staging-таблицу (все колонки `text`), а проверки и запись идут set-based на SQL.
2. **Один файл - одна транзакция.** Упал - откатился целиком, статус `failed`, можно перезапустить. Ошибка в строке файл не роняет: строка уходит в `payments_rejected` со всеми причинами.
3. **Повторный запуск защищен дважды.** Реестр файлов `load_files` по sha256 пропускает уже загруженные файлы. Номер файла в каждом платеже (`source_seq`) не дает старому файлу откатить новую версию, даже если реестр не сработал.
4. **Версии платежа упорядочивает только порядок файлов.** Исправление из следующего файла обновляет платеж. Две разные версии в одном файле не угадываю: отклоняю обе, верная приходит следующим файлом.
5. **Ошибка на уровне файла останавливает очередь.** Следующие файлы могут исправлять платежи из упавшего, грузить их раньше нельзя.
6. **"Период" в нарастающем итоге задается параметрами.** Дополнительно считаю итог с начала месяца - на случай, если имелся в виду месяц.
7. **"Добавлено" в статистике - только новые платежи.** Исправления считаются отдельно, в "обновлено".

## Как устроено

```
data/    contracts.csv, payments_001..003.csv
sql/     create_tables.sql           таблицы (можно запускать повторно)
         validate_payments.sql       проверки строк, дубли, решение insert/update/unchanged/reject
         apply_payments.sql          запись одним запросом
         payments_running_count.sql  нарастающий итог
etl/     load_payments.py            загрузчик
tests/   run_checks.py               интеграционный тест
docs/    test_data.md                что проверяет каждая строка тестовых файлов
```

Порядок загрузки: advisory lock (второй запуск сразу выходит с кодом 2) -> справочник договоров (если в нем ошибка, запуск останавливается) -> файлы `payments_NNN.csv` по номеру -> для каждого: реестр, чтение, проверки, запись, сверка, статус `success`.

| Таблица | Grain |
|---|---|
| `payments` | одна строка на `payment_id`, последняя корректная версия |
| `payments_rejected` | одна строка на отклоненную строку файла: сырые значения (jsonb) и все причины |
| `load_files` | одна строка на содержимое файла: статус, sha256, статистика, код ошибки |
| `contracts`, `ref_currency` | справочники договоров и допустимых валют (KGS, USD, EUR, RUB) |

В таблицах стоят `CHECK` и внешние ключи, хотя все уже проверено в SQL. Это последний рубеж: если в валидации баг, файл упадет, а не загрузит плохие данные тихо.

## Проверки качества данных

**Файл целиком** (Python). Не прошло - файл не грузится, очередь останавливается:
`FILE_ENCODING`, `FILE_HEADER_MISMATCH`, `FILE_EMPTY`, `FILE_CONTENT_CHANGED` (имя уже загружено с другим содержимым), `FILE_OUT_OF_ORDER` (номер меньше загруженного), `CONTRACTS_INVALID` (ошибка в справочнике).

**Каждая строка** (SQL). Строка уходит в rejects, остальные грузятся. Если ошибок несколько, будет несколько причин.

| Код | Проверка |
|---|---|
| `COLUMN_COUNT_MISMATCH` | в строке не 5 полей |
| `MISSING_*` | пустое поле (по каждому полю свой код) |
| `INVALID_PAYMENT_ID` | не `^[A-Z0-9_-]{1,30}$` |
| `CONTRACT_NOT_FOUND` | договора нет в справочнике |
| `INVALID_DATE` | не `ГГГГ-ММ-ДД` или такой даты нет (`2026-09-31`) |
| `DATE_BEFORE_CONTRACT_OPEN` | платеж раньше открытия договора |
| `DATE_IN_FUTURE` | позже сегодняшней даты |
| `INVALID_AMOUNT` | не `123` и не `123.45` (`12,50`, `NaN`, `1e3` не проходят) |
| `NON_POSITIVE_AMOUNT`, `AMOUNT_SCALE`, `AMOUNT_TOO_LARGE` | сумма <= 0, больше 2 знаков после точки, не влезает в `numeric(18,2)` |
| `INVALID_CURRENCY` | валюты нет в `ref_currency` |
| `DUPLICATE_ROW` | точная копия строки выше в этом же файле |
| `DUPLICATE_KEY_CONFLICT` | у одного `payment_id` в файле разные версии |

Перед проверками обрезаю пробелы, пустое значение считаю отсутствием, валюту привожу к верхнему регистру. ID не трогаю: `p1` и `P1` у источника могут быть разными платежами. Даты не привожу через `::date` сразу - на `2026-09-31` упал бы весь файл; сначала формат регуляркой, потом проверка, что такой день есть.

Сверка самого пайплайна по каждому файлу: `прочитано = добавлено + обновлено + без изменений + отклонено`. Не сошлось - откат с `RECONCILIATION_FAILED`.

## Дубли, исправления, повторный запуск

**Внутри файла.** Одинаковые строки: первая идет дальше, остальные `DUPLICATE_ROW`. Разные версии одного платежа: отклоняю все. Почему не "последняя строка" и не "максимальная дата": порядок версий по условию задают только файлы, `prov_dt` - дата проведения, а не время изменения, а если это два разных платежа с одним ID, выбор любой строки теряет платеж. Вариант "оставить положительную, если суммы отличаются только знаком" тоже отбросила: минус может быть сторно.

**Между файлами.** Корректная строка из более позднего файла обновляет платеж. Некорректная правка отклоняется, платеж остается прежним. Строка, совпадающая с текущей версией, ничего не меняет.

**Повторный запуск** решается по реестру:

| Ситуация | Что делаю |
|---|---|
| такой sha256 уже загружен | пропускаю; если имя другое - предупреждение в лог |
| имя уже загружено, sha256 другой | `FILE_CONTENT_CHANGED`: принятый файл не подменяется, исправления идут новым номером |
| номер меньше уже загруженного | `FILE_OUT_OF_ORDER` |
| файл был `failed` или `processing` | обрабатываю заново: прошлый запуск упал и откатился |

Уникальный индекс на имя файла частичный (`WHERE status = 'success'`), поэтому упавший файл можно перезалить исправленным под тем же именем. Если файл упал: смотрю `error_code` в `load_files`, после исправления просто запускаю загрузку снова.

## Статистика

```
payments_001.csv   processed | прочитано   29 | отклонено   21 | добавлено    8 | обновлено    0 | без изменений    0
payments_002.csv   processed | прочитано    8 | отклонено    1 | добавлено    4 | обновлено    2 | без изменений    1
payments_003.csv   processed | прочитано    4 | отклонено    0 | добавлено    3 | обновлено    1 | без изменений    0
ИТОГО                        | прочитано   41 | отклонено   22 | добавлено   15 | обновлено    3 | без изменений    1
Всего платежей в таблице: 15
```

"Обновлено" и "без изменений" - сверх ТЗ, без них не сходится сверка. Пустые строки в "прочитано" не входят, их число пишется в лог. Статистика каждого файла сохраняется в `load_files`, после повторного запуска ее можно посмотреть там.

## Нарастающий итог по датам

Функция `payments_running_count(date_from, date_to)` для каждой даты периода возвращает число платежей за день (`cnt_day`), итог с начала периода (`cnt_from_period_start`) и с начала месяца (`cnt_mtd`). Без параметров период - от первого до последнего платежа. Дни без платежей выводятся с нулем, считаются текущие версии платежей.

```sql
SELECT * FROM payments_etl.payments_running_count();                            -- весь период (тестовые данные - сентябрь 2026)
SELECT * FROM payments_etl.payments_running_count('2026-08-30', '2026-10-02');  -- видно сброс cnt_mtd 1 октября
```

## Тестовые данные и проверка

В `data/` каждая строка - отдельный кейс: корректные платежи, по примеру на каждую из 18 проверок строк, все случаи дублей, исправления в следующих файлах. `payments_003.csv` сохранен с BOM и CRLF, как из Excel. Что проверяет каждая строка - в [docs/test_data.md](docs/test_data.md).

`tests/run_checks.py` - интеграционный тест: в отдельной схеме прогоняет загрузку целиком и сверяет результат с ожидаемым. Итог: `Все проверки пройдены: 28`.

| Требование ТЗ | Блок теста |
|---|---|
| загрузка с проверками, статистика, ошибка строки не останавливает файл | 1 |
| отклоненные записи с причинами | 2 |
| корректная запись из следующего файла обновляет платеж | 3 |
| повторная обработка без дублей и изменений | 4 |
| нарастающий итог по датам | 5 |
| сверх ТЗ: принятый файл нельзя подменить; битый файл останавливает очередь | 6, 7 |

В тест не вошли, но обработаны в коде: параллельный запуск, старый файл в обход реестра (`VERSION_CONFLICT`), файл не по порядку, копия файла под другим именем, битый справочник.

## Допущения

- Порядок файлов - номер в имени `payments_NNN.csv`.
- Сумма <= 0 - ошибка: возвраты и сторно в этом формате не предусмотрены.
- Десятичный разделитель - точка, `12,50` не исправляю автоматически.
- Исправление может менять любые поля, включая `contract_id`.
- ID чувствительны к регистру.
- Отклоненная строка остается в rejects, даже если позже пришла исправленной.
